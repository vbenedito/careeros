# 2026-11-06 — The extension connects from the dashboard, and the tracking engine core is in

## Summary
The dashboard can now connect the browser extension to the signed-in account (#13), and both halves of the pure tracking engine landed: eligibility/activity (#14) and intervals with boundaries and recovery (#15). The Chrome adapters that wire the engine to real browser events (#16) are open for review in #51.

## Shipped
- #46 (closes #13): `/connect` page and `POST /api/extension/link` with Origin check, session check via `getUser()`, and a Postgres-backed rate limit (5 requests per rolling minute per user); pgTAP, integration and real-Chromium tests.
- #49 (closes #14): Engine A — `reduceSignals` decides whether a tracked domain is being studied right now; fails closed on startup; keeps only the matched tracked domain, never URLs.
- #50 (closes #15): Engine B — `step(state, event, now, env)` opens/closes intervals, computes 30-minute and local-midnight boundaries, and recovers from crash, sleep and clock jumps; tested with a fake clock across real time zones (São Paulo, Kolkata, New York fall-back, Santiago's skipped midnight) plus a seeded randomized invariant test.
- #51 (open, #16): Chrome adapters — serialized event queue, single storage write for state + new intervals, window-focus debounce, incognito never tracked.
- CI: Playwright Chromium is now cached and the apt dependency step skipped (5f097d7).

## Decisions
- The devlog agent lives only in the scheduled task, not in the repository; #48 was closed without merging ([#47 comment](https://github.com/vbenedito/careeros/issues/47)).
- A helper for HTTP requests in the dashboard, at the owner's review request: `lib/http/request.ts` never throws and validates bodies with Zod; the connect message got its own component (88d50c4, [#46](https://github.com/vbenedito/careeros/pull/46)).
- Spec clarifications proposed with the engine PRs and approved on merge (`specs/v0/01-tracking.md`): muted tabs don't count as audible (TRK-06); nothing is assumed before it is reported (TRK-01); every processed event is a checkpoint (TRK-13); clock steps back ≤ 2 s are noise, and a jump back > 30 min does not block tracking (TRK-15). Two new known limitations recorded in §5.
- `specs/v0/04-data-model.md`: `private.link_requests` and `consume_extension_link_quota()` documented as built.

## Problems & fixes
- #46 security review (Medium): `getClaims()` let a revoked access token mint a long-lived extension session — switched to `getUser()`; the link token is now bound to the caller's user id.
- #49 edge-case review (High): a heartbeat seeing a domain change and idle at once could start a media hold on the new domain; restored state was trusted after a crash — now re-observed via `RESYNC`.
- #50 edge-case review (High): repeated backward clock jumps could overlap recorded time, and a large clock correction could silently block tracking for months.
- #51 edge-case review (High): an offline disconnect with an expired token kept the session, so tracking restarted while the popup said "disconnected".
- All CI runs today passed.

## Lessons
- Keeping the engine pure (no Chrome APIs, no clock) is what made the nastiest cases — DST, skipped midnights, clock corrections — testable with a fake clock.
- The independent edge-case reviews found High issues in every engine/adapter PR; findings that belonged to later issues were written into those issues instead of being dropped.

## Post
The CareerOS extension can now be connected from the dashboard, and the core of its time-tracking engine landed today.

What moved:
- A /connect page issues a single-use token, checked against the live session and rate-limited in Postgres, so the extension gets its own session.
- The tracking engine is pure code: no Chrome APIs, no clock. It decides "is this a tracked study site right now?" and turns that into intervals, split at 30 minutes and at local midnight.
- Because the clock is injected, the tests cover DST fall-back, Santiago's skipped midnight, sleep, crashes and clocks jumping backwards.

The part I want to remember: AI agents implement each issue under the spec, and a separate agent reviews it for edge cases. That review found real High issues today, e.g. a large clock correction could silently block tracking for months, and an offline disconnect could leave tracking running while the UI said "disconnected". I decide scope and approve every merge; the reviews are why I trust what I approve.
